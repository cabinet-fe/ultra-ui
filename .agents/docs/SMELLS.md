# 坏味道基线

把重构当成好习惯融入日常的编码工作中。必须提前假设你在每一次编码时都有很大的可能产生巨型代码文件、重复代码、脱离项目规范的代码、死代码。对照本清单边写边收，不要等 review。偏离 `DEV-STANDARDS.md` 或项目技能的写法当场改回来。

Fowler《重构》第 3 章的固定子集，外加巨型文件与死代码。代码类始终适用。即使仓库没写任何其它规范也适用。

约束（两条都要守）：

1. **仓库覆盖**：DEV-STANDARDS、项目技能等已有标准说了算。它们认可的写法，忽略对应坏味道。
2. **判断而非违规**：每条都是带标签的启发式，不是硬性违规，不单独构成阻塞。工具已经强制检查的跳过。

对照本次改动，只标实际出现的。格式：是什么 → 怎么修。

- **巨型文件**：单文件职责过多、涨到难以一次读完或难以安全修改。→ 按职责拆开。
- **重复代码**：相同逻辑结构在本次改动的多处或多文件出现。→ 抽出共享结构，两处调用。
- **死代码**：本次引入或改动后不再被引用的函数、变量、类型、import、样式。→ 删掉，靠 git 回滚。
- **神秘的名字**：函数、变量或类型的名字看不出做什么或用途。→ 重命名；想不出名副其实的名字，说明设计本身含糊。
- **特性依恋**：方法用其他对象的数据比用自己的还多。→ 把方法搬到数据所在的类型上。
- **数据团**：同一组字段或参数总是一起出现（一个想诞生的类型）。→ 收成一个类型再传。
- **原始类型迷恋**：用原始类型或字符串代替本该独立的领域概念。→ 给这个概念一个小类型。
- **重复的开关**：同一类型上的 switch / if 级联反复出现。→ 用多态，或两处共享一份映射。
- **霰弹式修改**：一次逻辑变更要改很多文件。→ 把相关改动收到一个模块。
- **发散式变化**：一个文件或模块因多种不相关理由被改。→ 拆开，让每个模块只因一个理由变。
- **过度泛化**：为规格里没有的需求加的抽象、参数或钩子。→ 删掉，内联回去，直到真有需要。
- **消息链**：调用方不该依赖的 `a.b().c().d()` 长链。→ 把遍历藏进第一个对象的一个方法。
- **中间人**：类或函数主要在转手委托。→ 删掉它，直接调真正目标。
- **拒绝的遗产**：子类或实现者忽略或覆盖了继承的大部分。→ 不用继承，改组合。
